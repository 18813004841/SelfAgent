# SelfAgent 架构治理 Goal 计划

## Goal

检查并实现一套能在后续开发中持续生效的 SelfAgent 架构治理方案：明确模块边界和依赖方向，统一开发前检查入口，建立架构文档与 skill 的维护闭环，并用自动化检查和关键运行验证证明规则可执行。

## 当前基线

- 已有仓库级 `AGENTS.md`、`docs/architecture/` 文档和 `skills/selfagent-architecture/SKILL.md`。
- 工作台已有 `AGENTS.md`、`WORKBENCH_DEVELOPMENT_RULES.md`、`workbench-assistant` 和 `workbench-ui-flow`。
- 当前工程包含工作台、机器控制、代码检查、OpenAI Agent、示例和多个技能目录。
- 当前架构文档属于初步基线，部分边界、依赖和历史代码仍未完成审计。

## 成功标准

- 每个主要运行单元都有明确入口、职责、依赖方向、配置来源、数据/日志归属和验证命令。
- 新增功能能够通过仓库级规则判断应该落在哪个模块，不需要根据目录名称猜测。
- 跨模块调用有稳定契约、失败行为、生命周期和安全边界。
- 架构文档、AGENTS 规则和 skill 不互相矛盾，链接有效。
- 可以通过自动化检查发现：越界导入、未登记入口、失效文档链接、未声明端口/配置、运行产物误入源码目录等问题。
- 至少完成工作台、机器控制、代码检查和智能体四个主要运行单元的最小验证。

## 阶段计划

### Phase 1：架构事实审计

- [ ] 列出所有可执行入口：HTTP 服务、CLI、启动脚本、调度器、MCP、网关和打包脚本。
- [ ] 为每个入口记录调用方、工作目录、环境变量、端口、PID、配置文件和日志目录。
- [ ] 建立真实依赖图，区分 Python import、HTTP、子进程、文件和数据库依赖。
- [ ] 标记历史接口、legacy 分支、临时目录和未完成模块，不把推断写成规则。
- [ ] 核对 `Tools/local_codex` 与工作台 local_codex 启动器的职责关系。

交付物：更新后的模块清单、入口清单、依赖图和待确认项。

### Phase 2：边界和契约固化

- [ ] 明确工作台与外部运行单元的编排边界。
- [ ] 明确机器控制中心、Worker、共享协议和客户端打包边界。
- [ ] 明确代码检查的输入、成功基线、模型服务和报告输出边界。
- [ ] 明确 OpenAI Agent 的认证、网关、令牌和调用边界。
- [ ] 为每个跨模块接口补充输入、输出、错误、超时、重试、停止和幂等约定。
- [ ] 决定根目录 `requirements.txt` 与各模块依赖文件的责任关系。

交付物：更新 `docs/architecture/模块边界.md` 和相关模块 README/规则。

### Phase 3：规则与 skill 落地

- [ ] 保持根目录 `AGENTS.md` 作为所有开发任务的入口。
- [ ] 保持 `selfagent-architecture` skill 只描述架构治理，不复制具体模块规则。
- [ ] 为架构变更建立统一模板：事实、变更、影响、验证、待确认项。
- [ ] 规定新增模块、端口、配置、存储、日志、进程和外部依赖必须同步文档。
- [ ] 为工作台、代码检查、机器控制和智能体补齐必要的模块级规则入口。
- [ ] 明确 skill 目录中缺少 `SKILL.md` 的目录是占位、废弃还是待实现。

交付物：规则文件、skill、架构变更模板和模块入口索引。

### Phase 4：自动检查实现

- [ ] 增加架构检查脚本，检查文档链接、入口登记和模块目录声明。
- [ ] 检查禁止的依赖方向，例如独立工具反向导入工作台页面或路由。
- [ ] 检查端口、环境变量、配置文件和启动器登记是否一致。
- [ ] 检查运行日志、缓存、临时数据库和用户凭据是否进入源码或 Git 跟踪。
- [ ] 检查新增 Python/JS 模块是否有对应测试、语法检查或最小验证命令。
- [ ] 将检查接入本地命令或代码检查流程；确认失败时不会修改成功基线。

交付物：可重复执行的架构检查命令和失败报告格式。

### Phase 5：运行验证和持续维护

- [ ] 启动工作台并验证页面、View、ProcessManager 和至少一个外部启动器。
- [ ] 验证机器控制中心与 Worker 的健康检查或最小请求。
- [ ] 执行代码检查 CLI 的安全样例，确认成功基线和失败行为。
- [ ] 启动智能体网关，验证本地接口和令牌不泄露到日志或响应。
- [ ] 验证规则变更能被后续任务发现，且模块级规则优先级清晰。
- [ ] 每次架构变更记录日期、依据、影响范围和验证结果。

交付物：验证记录、已知限制和下一轮技术债清单。

## 必须提前放入计划的事项

### 1. 边界审计

不能只画目录图。必须同时审计 import、HTTP、子进程、文件、数据库和环境变量依赖，否则会漏掉隐式耦合。

### 2. 配置和依赖治理

需要提前决定根 `requirements.txt` 是否继续保留，以及模块是否统一使用 Conda、独立 pyproject 或其他环境。还要定义配置优先级：默认值、环境变量、本地配置和命令行参数。

### 3. 安全边界

计划中必须包含 OAuth token、API key、MCP 凭据、日志脱敏、子进程命令、文件路径穿越、仅本地绑定和外部端口暴露检查。

### 4. 生命周期治理

每个被工作台启动的进程都需要定义启动、停止、重启、崩溃检测、孤儿 PID、端口占用和退出码处理。

### 5. 数据和迁移

需要明确 SQLite/JSON/日志/报告/缓存的所有者、目录、保留周期、备份方式、并发访问和版本迁移策略。

### 6. API 兼容性

页面与 View、工作台与启动器、中央服务与 Worker、代码检查与模型服务之间都需要记录版本、错误码、超时和兼容策略。

### 7. 可观测性

统一事件名、日志级别、关联 ID、耗时、健康检查和失败报告格式，避免只依赖控制台输出。

### 8. 测试策略

提前规定静态检查、单元测试、接口测试、进程集成测试和手工 UI 验证各自负责什么，避免只验证业务函数而没有验证真实入口。

### 9. 变更和回滚

架构调整需要记录影响范围、迁移顺序、兼容窗口、回滚步骤和旧接口下线条件，尤其是启动器、端口和持久化结构变更。

### 10. 文档生命周期

明确谁维护架构文档、何时必须更新、如何清理失效链接和待确认项，避免文档再次变成一次性报告。

## 风险与应对

| 风险 | 应对 |
| --- | --- |
| 历史代码与推荐架构不一致 | 区分当前事实和目标规则，按功能逐步迁移 |
| 根依赖与模块环境冲突 | 先盘点实际运行命令，再决定统一或隔离 |
| 架构检查过于严格阻塞开发 | 先报告模式，确认规则后再启用阻断模式 |
| 工作台继续承载 legacy 接口 | 新接口遵循 View 边界，旧接口单独登记迁移计划 |
| 运行产物污染 Git | 补充 `.gitignore`、目录所有者和清理策略 |
| 文档与代码漂移 | 将入口、端口和链接检查加入自动化验证 |

## Goal 完成验收

- [ ] Phase 1 至 Phase 5 的必要交付物已完成或明确阻塞原因。
- [ ] 架构文档、AGENTS、skill 和模块 README 的职责没有重复冲突。
- [ ] 自动检查命令可执行，并能对一个故意制造的违规样例报错。
- [ ] 关键运行单元完成最小健康验证。
- [ ] 所有未完成项进入明确的技术债或待确认清单。
- [ ] 形成一份最终架构基线和下一阶段维护计划。

## 当前不应直接做的事情

- 不在没有依赖审计前把代码搬入根目录 `src/`。
- 不为了“统一架构”一次性重写 `server.py`、启动器或所有 legacy 接口。
- 不把日志、缓存、临时数据库和本地凭据纳入架构源码。
- 不把目录名推断成已确认职责。
