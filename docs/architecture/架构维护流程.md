# 架构维护流程

## 适用时机

新增或移动目录、服务、页面、启动器、工具、依赖、端口、数据路径和跨模块调用时使用。局部缺陷修复遵循目标模块规则，不因一次修复改写全局架构。

## 流程

1. 搜索真实入口、调用方、配置、存储、日志和现有测试；记录当前代码事实。
2. 依据[模块边界](模块边界.md)判断归属，优先复用现有运行单元。
3. 定义最小契约：入口、输入、输出、错误、配置、日志、生命周期和停止条件。
4. 保持依赖方向：工作台编排外部单元，独立单元不反向依赖工作台页面或路由。
5. 实现后检查入口注册、导入路径、启动器注册、页面登记、默认值和错误分支。
6. 只更新受影响的架构文档和模块规则；删除失效链接，把无法证明的内容留在待确认事项。

## 文档分工

- `docs/architecture/架构总览.md`：模块关系、调用关系、当前事实和架构级待确认项。
- `docs/architecture/模块边界.md`：稳定入口、默认值、接口契约和归属判断。
- `docs/architecture/架构维护流程.md`：变更时如何判断和验证。
- 模块内部细节留在模块已有 README、AGENTS.md、开发规则或专用文档中。

## 验证

至少检查真实文件路径、导入和注册关系、配置默认值、Markdown 相对链接。涉及工作台页面时执行工作台 UI skill 的 HTML → JS → view → 业务闭环检查；涉及进程时验证启动器和状态查询；涉及依赖时说明实际使用的环境和命令。

仓库级架构变更后执行：

```powershell
python scripts/check_architecture.py
```

该检查覆盖架构文档链接、入口清单和独立模块对工作台的反向导入。它不替代模块自己的测试。

## 当前维护命令

- `python scripts/check_architecture.py`：检查架构文档链接、入口登记和反向依赖。
- `python scripts/run_code_review_validation.py`：使用临时仓库验证发现问题时更新基线、执行失败时保留基线。
